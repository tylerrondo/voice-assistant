# PR-13 — Playwright-покрытие сценария «Driver Standard Trip»

## Ключевое архитектурное решение (требует подтверждения)
ТЗ требовало `ScenarioSource = Built-in` с активным набором
**Driver Standard Trip**. До PR-13 `builtin.json` содержал 3 других,
общих инфраструктурных сценария (`voice.recognized`,
`interaction.echo`, `interaction.delayed`) — они не имели отношения к
driver-flow и никогда не были "настоящим" продуктовым содержимым,
только заглушкой для PR-11.

**Решение (принято мной, без блокирующего запроса на разработчика —
явно делегировано):** `builtin.json` заменён на 5-сценарийный
Driver Standard Trip (`accept-order → arrived → start-trip →
finish-trip → become-available`), как и было изначально описано в
исходном обсуждении Platform Scenario Specification.

**Последствия:** это меняет поведение уже принятого builtin-набора.
Обновлены все существующие тесты, которые были завязаны на старые 3
сценария:
- `tests/playwright/utils/helpers.ts` — `SCENARIO_TRIGGERS` (3→5),
  `completeInteractiveSessionWithInject` default `steps` (3→5).
- `tests/playwright/interactive.spec.ts` — все "3" → "5"
  (`current-step`, "Fully confirmed", "Skipped").
- `tests/playwright/report.spec.ts` — `ManualValidation.results`
  length 3→5.
- `tests/playwright/scenario-source.spec.ts` — тест на "builtin после
  неудачной загрузки" ожидал `totalScenarios=3`, теперь 5. Тестовый
  fixture-файл `driver-standard-trip.json` (2 сценария, использовался
  только для проверки JSON File upload) переименован в
  `custom-scenario-upload.json` во избежание путаницы с настоящим
  builtin-набором, который теперь называется так же.
- `apps/voice-demo/src/InteractiveScriptMap.ts` — переписан с нуля:
  промпты/ожидаемые фразы для 5 driver-триггеров на 4 языках вместо
  старых 3 инфраструктурных.
- `apps/voice-demo/src/App.ts` — убран устаревший хардкод `|| 3` в
  подсчёте `totalScenarios`.

**Если это решение нежелательно** — откатить `builtin.json` к старому
3-сценарийному набору достаточно просто (файл маленький), но тогда
PR-13 нужно перепроверять на новом фикстур-файле через
`ScenarioSource = file`, а не `Built-in`, и переформулировать
прекондицию ТЗ.

## Что покрыто тестом
`tests/playwright/driver-standard-trip.spec.ts`:
1. **Automatic** — Built-in активен, Run All, отсутствие ошибок,
   Progress = "Done", Execution Log = 5 действий в правильном
   порядке, JSON Report содержит верные ScenarioSource/Id/Name/File,
   PASS для всего набора.
2. **Interactive** — пошаговое прохождение всех 5 сценариев с
   проверкой Session State / Current Step / Progress / Execution Log
   после каждого шага, финальное состояние `finished`, тот же набор
   метаданных в отчёте, что и в Automatic.
3. **Порядок** — Execution Log в строгом порядке в обоих режимах.
4. **Повторяемость** — два запуска подряд дают одинаковый результат;
   Execution Log второго запуска не содержит записей первого.
5. **Reset** — после `finished` сброс перезапускает сессию с первого
   сценария; Execution Log не содержит записей завершённого прогона.

Все проверки — только через `page.getByTestId(...)` (контракт PR-12).
Не проверяются: STT, TTS, качество распознавания, микрофон, Browser
Speech API — как и требовало ТЗ.

## Важное открытие о реальном состоянии Interactive Runner
Реализация оказалась немного отличной от наивного прочтения ТЗ, что
пришлось выяснять по коду (`App.ts`, `SessionController.ts`,
`StepState.ts`) перед тем, как писать корректные проверки:

- Выбор **Interactive** в Validation Mode **сразу** стартует сессию:
  никакого отдельного "idle"-состояния с "0 / 5" не существует —
  сразу `session-state = "running"`, `current-step = "1 / 5"`,
  `progress-value = "0%"`.
- Первый клик "Next Step" **выполняет** первый сценарий (инжектит
  действие) и переводит в `waiting-tester`.
- Каждый следующий клик "Next Step" (после подтверждения) **и**
  фиксирует текущий сценарий, **и** автоматически стартует
  следующий (`autoStartNextStepIfNeeded`) — то есть на один клик
  делается две вещи. Итог: для 5 сценариев нужно 6 кликов "Next
  Step" (1 старт + 5 подтверждений).
- **Reset** не возвращает в "idle" — он немедленно перезапускает
  сессию (то же состояние, что и при первом выборе Interactive:
  `running` / `1 / 5` / `0%`), просто с очищенным Execution Log
  (хотя и не полностью пустым — там сразу появляется маркер `[Step]`
  для первого сценария).
- `progress-value` считается по **сценариям**, не по шагам внутри
  сценария, и всегда форсируется в `100%` при `finished`, независимо
  от арифметики.

Это задокументировано прямо в тесте (комментарии у каждого блока),
чтобы будущие PR по другим сценариям не наступали на те же грабли.

## Addendum — ответ на ревью

**1. Жёсткая привязка к количеству шагов — исправлено.**
Тест больше не хардкодит `5` или список из пяти триггеров. Он читает
`packages/scenario-engine/src/scenarios/builtin.json` напрямую
(`readFileSync` + `JSON.parse`) и вычисляет `TRIGGERS_IN_ORDER`/`TOTAL`
из содержимого файла. Если в driver-standard-trip.json завтра
появится шестой шаг, тест не потребует правок — он подстроится
автоматически, и будет продолжать проверять реальное поведение
приложения.

**2. Жёсткая привязка к английским строкам — исправлено там, где это
осмысленно.**
- `session-state` — было `.toHaveText("running"/"finished"/...)`,
  стало `.toHaveAttribute("data-state", "running"/"finished"/...)`.
  Атрибут `data-state` — это literal `StepState` enum-значение
  (`idle`/`waiting-tester`/`running`/`paused`/`finished`),
  устанавливаемое явно как контракт (`App.ts`:
  `intSessionState.setAttribute("data-state", state)`), а не то, что
  "просто пока не переведено".
- `report.Summary.status === "PASS"` и `report.ScenarioId/ScenarioName`
  берутся из JSON-отчёта, а не из текста на панели.
- `"Done"` (текст Automatic-прогресса, который ДЕЙСТВИТЕЛЬНО
  локализуется — `getProgressDoneLabel()`) убран из проверок; вместо
  него — `run-all-button` снова `enabled` после завершения прогона
  (стабильный, нелокализуемый сигнал).
- `current-step`/`progress-value` — числа `N / TOTAL` и `NN%` не
  являются переводимым текстом (это данные, не UI-строка на языке
  интерфейса), поэтому оставлены как есть — но теперь вычисляются из
  `TOTAL`, а не хардкодятся.

**3. Проверка соответствия JSON и выполненного сценария — добавлено.**
`expect(report.Summary.totalScenarios).toBe(TOTAL)`, где `TOTAL` —
длина `scenarios[]` в реальном файле. Это именно то независимое от
хардкода сопоставление "в файле N сценариев" ⇄ "в отчёте N
сценариев", которое просил ревьюер.

**4. Негативный тест (сломанный шаг → FAIL) — НЕ добавлен, и вот
почему.**
Я специально не стал писать этот тест, вместо того чтобы сделать вид,
что он что-то проверяет. Причина: в текущей реализации Automatic
verification (`App.ts`, обработчик Run All) **нет вообще никакой
логики определения провала шага** — `verification.passed` всегда
равен `totalScenarios`, `verification.failed` всегда `0`, безусловно.
Это не тестовая проблема — это архитектурный пробел приложения:
физически невозможно написать тест "один шаг сломан → отчёт
показывает FAIL", потому что ни один код-путь сегодня не производит
FAIL. Тест на это либо был бы бессмысленным no-op (не может упасть
при любом изменении логики), либо потребовал бы тайком добавить
реальную логику проверки успеха/неудачи шага в сам PR-13 под видом
теста — это отдельная, отдельно обсуждаемая доработка Verification
pipeline. Предлагаю завести её отдельным пунктом (PR-13a? или в
рамках PR-14) прежде, чем писать этот конкретный негативный тест.
