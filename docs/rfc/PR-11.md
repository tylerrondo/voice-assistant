# PR-11 — External JSON Scenarios

## Цель
Перевести Validation Bench со встроенных сценариев
(`packages/scenario-engine/src/BuiltinScenarios.ts`) на внешние
JSON-сценарии, соответствующие Platform Scenario Specification v2.0.
После PR любой корректный JSON-сценарий выполняется без изменения
исходного кода и без перекомпиляции приложения.

## Что реализовано

### 1. `ScenarioProvider` (packages/scenario-engine)
```ts
interface ScenarioProvider {
    load(): Promise<ScenarioSet>
}
```
Две реализации:
- `BuiltinScenarioProvider` — читает `packages/scenario-engine/src/scenarios/builtin.json`.
- `JsonScenarioProvider` — валидирует произвольный распарсенный JSON
  (файл, выбранный пользователем в браузере через `FileReader`).

Runner (`ScenarioEngine`/`ScenarioRegistry`) не знает про
`ScenarioProvider` вообще — он как и раньше работает только с
`Scenario { name, trigger, steps }`. Мост между внешним JSON и
внутренней моделью — `ScenarioSetLoader.loadScenarioSetIntoRegistry()`.

### 2. Формат JSON — Platform Scenario Specification v2.0
Поддерживаются обе формы активации сценария:
- `"trigger": "voice.accept-order"` (v1, обратная совместимость);
- `"activation": { "type": "voice", "value": "voice.accept-order" }` (v2,
  предпочтительно — задел под будущие каналы: button/fsm/timer/geo).

Все остальные поля (`id`, `description`, `category`, `difficulty`,
`expectedPhrase`, `aliases`, `tags`, ...) — метаданные для будущих
потребителей (Driver Training, Certification, Analytics) и Validation
Bench их не использует и не проверяет по существу, только пропускает.

### 3. Валидация (`ScenarioSetValidator.ts`)
Единая точка проверки и для builtin.json, и для пользовательского
файла: `version` поддерживается, есть `id`/`name`, `scenarios` не
пуст, у каждого сценария есть `name`, `activation`/`trigger` и
непустой `steps`, каждый `step` — корректного `kind`. При ошибке —
`ScenarioSetValidationError` с человекочитаемым сообщением.

### 4. UI — Scenario Source
Добавлен блок **Scenario Source: (●) Built-in / ( ) JSON File** с
кнопкой **Choose File...**. При успешной загрузке отображается имя
файла (`driver-standard-trip.json` / `builtin.json`). При ошибке —
`alert` с описанием проблемы, и активный источник **не меняется**
(остаётся последний рабочий набор — builtin или ранее загруженный
файл), поэтому Run All и Interactive продолжают работать.

Automatic и Interactive используют один и тот же `ScenarioRegistry`
(он был общим и раньше, через `EmulatorContract`) — при смене
источника он полностью перезаполняется (`ScenarioRegistry.clear()` +
regisтрация новых сценариев), так что оба режима сразу видят новый
набор.

### 5. Отчёт
Добавлены поля верхнего уровня:
```json
"ScenarioSource": "builtin" | "file",
"ScenarioId": "driver-standard-trip",
"ScenarioName": "Driver Standard Trip",
"ScenarioFile": "driver-standard-trip.json"
```
(`ScenarioFile` — `null`, если источник `builtin`.)

## Отклонение от исходного ТЗ
`builtin.json` физически лежит в `packages/scenario-engine/src/scenarios/`,
а не в `packages/scenario-engine/scenarios/` — иначе `tsc` (с
`resolveJsonModule`) ругается на файл вне `rootDir`. Поведение и
контракт не меняются, только путь на диске.

## Playwright
`tests/playwright/scenario-source.spec.ts`:
1. Built-in — источник по умолчанию, используется в Run All.
2. Валидный JSON-файл заменяет активный набор сценариев, отчёт содержит
   правильные `ScenarioSource`/`ScenarioId`/`ScenarioFile`.
3. Некорректный JSON (синтаксис) — ошибка, Built-in остаётся активным.
4. JSON, не проходящий контракт (нет `scenarios`) — ошибка, Built-in остаётся активным.
5. Interactive и Automatic видят один и тот же переключённый набор
   (проверяется через `#inject-select`).

Существующие тесты (`smoke.spec.ts`, `automatic.spec.ts`,
`interactive.spec.ts`, `report.spec.ts`) не изменялись и продолжают
проходить: они уже читают количество сценариев из отчёта
(`report.Summary.totalScenarios`), а не хардкодят его, и порядок/
значения builtin-триггеров не изменились.

## Не входит в PR
Редактор сценариев, каталог сценариев, удалённое хранилище, загрузка
по URL, обучение водителей, экзамены, новые типы шагов — как и
оговаривалось изначально.

## Addendum — ответ на ревью (data-testid)

По замечанию ревьюера: изначально `data-testid` были только у
`scenario-file-name` и `scenario-error`, а `scenario-source.spec.ts`
местами обращался к элементам через CSS `#id`. Исправлено — добавлены
стабильные хуки, не зависящие от текста/локализации:

| data-testid | Элемент |
|---|---|
| `scenario-source-builtin` | radio "Built-in" |
| `scenario-source-file` | radio "JSON File" |
| `scenario-file-input` | `<input type="file">` |
| `scenario-choose-file-button` | кнопка "Choose File..." |
| `scenario-file-name` | текст активного файла (был и раньше) |
| `scenario-error` | блок сообщения об ошибке (был и раньше) |

Все шесть добавлены в `smoke.spec.ts` → тест
"required data-testid hooks exist for automated testing", как и
остальные хуки проекта. `scenario-source.spec.ts` переведён на
`page.getByTestId(...)` везде, где раньше использовался `#id`.
(`#mode-select`, `#input-source-select`, `#inject-select` оставлены
как есть — это существовавшие до PR-11 элементы, и весь остальной
тест-сьют обращается к ним так же, через `#id`.)
